# Catalogs in PostgreSQL + Authenticated Forms + Splunk Lookup Publishing

## Key findings that shaped this plan
- **None of the three catalogs exist as files in the repo or DB.** `Ruleset.csv` lives only on the Splunk search head (app `search`, ~1,782 rows; confirmed columns `RuleNum` (4-digit text), `RuleName_EN`, `GID` — mostly `Default`). Any extra columns are discovered at import time. Customer Information and Fix Source type exist only as conventions: `[Short]` name prefixes, `g<tenant>` index prefixes (`Fix_Index = "G"+GID`), and the required free-text `Fix_Source Type` field (e.g. `"QiAnXin EDR"`) in every CITIC ticket table.
- PostgreSQL is already set up: psycopg 3 `PostgresStore` with idempotent `_ensure_schema()` in `postgres_store.py`; no ORM/migration framework.
- The detection draft workflow is the exact pattern to reuse: MCP tool returns a draft envelope with `expected_fingerprint`; Save goes browser → host RPC `/soc-agent-config` → `runAuthCommand` → `auth_cli` (actor from DB session) → service gated by a write flag.
- Splunk write path today has only saved-search CRUD; **lookup publishing is new client surface** (gated by a new flag). `outputlookup` is blocked in the agent query policy — publishing bypasses the agent policy via a dedicated service path.

## Decisions taken by best judgment (unanswered questions — flip if wrong)
1. **RuleNum globally unique** (`UNIQUE`), 4-digit text with leading zeros preserved. Evidence: one shared Ruleset.csv pool, global `<RuleNum>_*.csv` lookup filenames, CITIC SPL requires a unique 4-digit rulename.
2. **Fix Source type = per-customer source systems**: record maps a customer's source system → verified `Fix_Source Type` value + default `Fix_Index`; unique per (customer, value).
3. **Customer Information = identity + tenant mapping**: customer_id, verified code/short name, display name, lifecycle status, tenant number, GID.
4. **Editing: any authenticated SOC user** (`requireUser` + explicit Save); **publishing: `requireAdmin`** (production Splunk write).

## Stage A — Database schema (`postgres_store.py` + new `catalog/store.py`)
Versioned migrations without new dependencies: a `soc_catalog_migrations` table + ordered `[(version, sql)]` list applied in order (idempotent), applied in `_ensure_schema()` path.

- `soc_customer`: `customer_id PK`, `customer_code UNIQUE NOT NULL`, `display_name NOT NULL`, `tenant_number`, `gid UNIQUE (nullable)`, `lifecycle_status CHECK IN ('active','provisioning','suspended','retired')`, `notes`, `revision INT NOT NULL DEFAULT 1`, `archived_at NULL`, `created_at/updated_at/created_by/updated_by`.
- `soc_rule_catalog`: `rule_id PK`, `rule_number TEXT CHECK '^[0-9]{4}$'` (non-unique index initially — **UNIQUE added only after duplicate reconciliation** via a pending migration step applied by explicit CLI command), `rule_name_en NOT NULL`, `rule_name_zh`, `severity CHECK IN ('info','low','medium','high','critical')`, `description`, `remediation`, `status CHECK IN ('draft','active','disabled','retired')`, `customer_id NULL FK→soc_customer` (NULL = shared; GID never used for ownership), `gid` raw provenance value, `revision`, `archived_at`, timestamps/actors.
- `soc_fix_source_type`: `source_type_id PK`, `customer_id FK NOT NULL`, `system_name NOT NULL`, `fix_source_type_value NOT NULL`, `default_fix_index` (validated = `'G'||customer.gid`), `description`, `revision`, `archived_at`, `UNIQUE(customer_id, fix_source_type_value)`.
- `soc_catalog_history`: `history_id BIGSERIAL PK`, `catalog CHECK IN ('customer','rule','fix_source_type')`, `record_id`, `revision`, `action CHECK IN ('create','update','archive','restore','publish')`, `actor NOT NULL`, `reason`, `before_json JSONB`, `after_json JSONB`, `changed_at`; indexed (catalog, record_id, changed_at).
- `soc_catalog_publications`: `publication_id PK`, `catalog`, `lookup_name`, `content_checksum`, `destination`, `actor`, `published_at`, `outcome CHECK IN ('pending','published','failed','rolled_back')`, `error`, `content_snapshot` (full CSV for rollback), `validated BOOL`.
- Import: `soc_catalog_import_batches` (batch_id, source, actor, report JSONB) + `soc_catalog_staging` (batch_id, row_number, payload_json, warnings).
- Every record mutation = one transaction: record write + history row. Optimistic locking via `expected_revision` (mismatch → `catalog_conflict` + current revision), mirroring detection fingerprints. Archive-by-default; store rejects archive/delete of records still referenced (customer referenced by rules/fix-source-types; published snapshot references recorded).

## Stage B — MCP tools + service (new package `unified_mcp_server/catalog/`)
`model.py` (frozen dataclasses + `from_payload`), `validation.py` (per-field error messages, enums, 4-digit rule number, rule-name pattern, code format, translations), `store.py` (per-call connections, transactions, revision checks, history, search/filter/pagination), `service.py` (facade), `tools.py` with the exact `register_tools(server, *, get_runtime, fresh_runtime, execute, success, failure, service_error)` signature; wire into `Runtime`/`create_server()` in `server.py`; add package to `pyproject.toml` setuptools packages.

Tools — reads (→ `READ_ONLY_TOOLS`): `catalog_list_rules`, `catalog_get_rule`, `catalog_list_customers`, `catalog_get_customer`, `catalog_list_fix_source_types`, `catalog_get_fix_source_type`, `catalog_get_record_history`, `catalog_preview_publication` (generates CSV + validation report, read-only).
Draft writes (→ `ACTION_CATALOG` group "Catalogs", always-ask like detections via new `CATALOG_ACTION_TOOLS`): `catalog_write_rule`, `catalog_update_rule`, `catalog_write_customer`, `catalog_update_customer`, `catalog_write_fix_source_type`, `catalog_update_fix_source_type` (return draft envelopes with `expected_revision`, `save_requires_explicit_action: true` — no DB write), plus `catalog_archive_record`.
Publishing is **not** an agent tool — operator-only via UI RPC (Stage D). Customer-scope enforcement lives in `store.py` queries/writes keyed on server-resolved identity; direct record-ID requests resolve scope server-side only.

## Stage C — Splunk lookup publish path (`splunk_client.py`, `catalog/publish.py`)
- New `SplunkClient.upload_lookup_contents(name, app, owner, contents)` via `POST /servicesNS/{owner}/{app}/data/lookup-table-files/{name}` (inline contents); fallback: server-side oneshot `| outputlookup` job marked controlled-write (not agent query policy). Gated by new env `SPLUNK_ALLOW_LOOKUP_WRITE` (default false) + `SPLUNK_LOOKUP_APP` (default `search`), `SPLUNK_LOOKUP_OWNER` (default `nobody`).
- Publish flow: select catalog → validate all rows (identifiers, FKs, required fields, customer scope, **no duplicate rule numbers** — publish blocked until reconciled) → generate CSV in the current lookup format (column set captured at import; RuleNum written as text preserving leading zeros) → sha256 checksum → gated upload → read back via `| inputlookup` oneshot and compare checksum → write `soc_catalog_publications` row (checksum, destination, actor, timestamp, outcome) atomically. Previous published snapshot kept for one-click rollback (new publication record, `rolled_back` linkage). Splunk failure → outcome `failed`, DB revision untouched, never reported as success.
- Record status model for UI: Saved (DB) / Pending publication (changed vs latest published snapshot) / Published / Publication failed — derived from latest publication record + per-record revisions.

## Stage D — Host, auth_cli, RPC endpoints
- `auth_cli.py`: `save-catalog-record`, `archive-catalog-record`, `publish-catalog` commands; actor resolved from the Postgres session (same as `save-detection`), anonymous rejected.
- `host.js` `handleEndpoint` cases: `catalog-list`, `catalog-get`, `catalog-history`, `catalog-publications`, `save-catalog-record`, `archive-catalog-record` (requireUser), `catalog-preview-publish`, `publish-catalog` (requireAdmin), each with a `validateCatalog*Payload` shape validator and the existing error mapping.
- `policy.js`: reads → `READ_ONLY_TOOLS`; drafts/archive → `ACTION_CATALOG` + `CATALOG_ACTION_TOOLS` (always-ask in host.js `tools/pre-execute`).

## Stage E — Client UI (`packages/soc-agent-client`)
- `src/client/catalog.ts`: tool-name constants, `CatalogDraftEnvelope` types, `parseCatalogEnvelope`, `formFromRecord`/`recordFromForm`, per-field validators (mirrors `splunkDetection.ts`).
- `src/client/CatalogToolview.tsx` + `.module.css`: keyed toolviews for the 7 draft tools; Field/SelectField/Toggle pattern; status machine editing/saving/saved/failed; per-field `role="alert"` validation; Save via `rpc(connection,'save-catalog-record',…)`; archive with inline confirm; history + diff using the harness `DiffBlock` primitive.
- `src/client/CatalogManager.tsx`: management page on pathname `/catalogs` (AdminConsole pattern: pathname branch in `index.ts`, route served by host.js) — searchable three-tab list → record editor, revision history with diffs, publication panel (preview diff vs current published snapshot, confirm, status pills Saved/Pending/Published/Failed, publication history with checksum/actor/timestamp, rollback with confirm). Register installer in `src/client/index.ts`.

## Stage F — Migration, docs, tests
- `catalog_cli.py`: `import-ruleset` reads live `Ruleset.csv` via oneshot `| inputlookup Ruleset.csv` (read-only path), loads staging, discovers the full column set, and emits a reconciliation report: source vs imported counts, duplicate rule numbers, missing fields, severity inconsistencies, unknown customer mappings, original rows preserved. `promote` (explicit, after team review) moves staged rows in; `apply-unique-constraint` applies the pending rule-number UNIQUE migration. No auto-publish; generated CSV compared column-by-column against the live original before switch.
- Docs: `server/README.md` (Postgres scope change), `README.md`, `BACKGROUND.md`, `AGENTS.md`, `skills/detection-engineering/SKILL.md` (catalog replaces hand-editing Ruleset.csv).
- Tests: Python `test_catalog_store/validation/service/publish.py` (fake-psycopg + fake Splunk client patterns), update `test_server_tools.py` exact tool set; Node `policy.test.js` counts + new host validator tests; client `tests/catalog.test.ts` (pure helpers + source-assertion style).
- Verification run: `uv run pytest` (apps/soc-agent/server), `npm test` (apps/soc-agent and packages/soc-agent-client).

## Delivery order
A → B → C → D → E → F, tests green at each stage. Rollout remains read-only comparison until reconciliation passes; editing enabled after promote; publishing after CSV-format validation against the live lookup.

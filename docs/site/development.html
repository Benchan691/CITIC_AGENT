No active lint/format hooks exist (lefthook.yml is commented examples) — match surrounding style manually. All suites run offline (in-memory doubles, fake transports, local subprocesses); nothing is skipped; no CI exists at the root.

Dependency model and generated boundary

The vendored harness's pnpm workspace includes this repo — SOC packages resolve via workspace:* and one link:. Two Python dependency files exist by design: root requirements.txt lists external pnpm plugins (count-validated against setup.sh's hardcoded PLUGIN_NAMES), while the server's pyproject.toml/uv.lock are the real Python dependencies. packages/soc-agent-client/lib/ is tracked generated output — rebuild after client changes and commit source + bundle together.

Adding or changing an MCP tool — six contracts

  1. Python registration (register_tools module + readOnlyHint; never ctx/account_id params).
  2. Raw allowlist entry in cordis.patch.yml.
  3. Qualified policy entry in policy.js (read list or ACTION_CATALOG).
  4. Client labels/views if the tool needs special presentation.
  5. Tests on both tiers (test_server_tools.py exact set; policy.test.js/skills.test.js counts — currently 29/41/12).
  6. Documentation (reference/MCP_TOOL_CATALOG.md, routing page, traceability matrix).

Vendor changes stay reproducible: configure via cordis.patch.yml rows, file-level changes via patches/*.patch (+ the pinned spec in requirements.txt), persona via the citic-soc preset — never edit vendored sources.

Known coverage gaps

No end-to-end browser tests; draft→UI→send chain tested only in segments; real-SQL behaviors run against doubles; setup.sh/update.sh untested; retained-code non-registration asserted only negatively. Full detail: TEST_COVERAGE_MATRIX.md.

Dependency model and generated boundary

The vendored harness's pnpm workspace includes this repo — the eight SOC browser packages resolve via workspace:* and one link:. Two Python dependency files exist by design: root requirements.txt lists external pnpm plugins (count-validated against setup.sh's hardcoded PLUGIN_NAMES), while the server's pyproject.toml/uv.lock are the real Python dependencies. Each packages/soc-agent-*/lib/ directory is tracked generated output — rebuild the owning package after source changes and commit source + bundle together.

Adding or changing an MCP tool — six contracts

  1. Python registration (register_tools module + readOnlyHint; never ctx/account_id params).
  2. Raw allowlist entry in cordis.patch.yml.
  3. Qualified policy entry in policy.js (read list or ACTION_CATALOG).
  4. Browser package labels/views if the tool needs special presentation.
  5. Tests on both tiers (test_server_tools.py exact set; policy.test.js/skills.test.js counts — currently 30/42/12).
  6. Documentation (reference/MCP_TOOL_CATALOG.md, routing page, traceability matrix).

Vendor changes stay reproducible: configure via cordis.patch.yml rows, file-level changes via patches/*.patch (+ the pinned spec in requirements.txt), persona via the citic-soc preset — never edit vendored sources.

Known coverage gaps

Browser smoke uses deterministic fixture data and screenshot baselines; draft→UI→send chain and real-SQL behaviors remain tested in segments or against doubles; setup.sh/update.sh still require deployment-environment validation; the retained Splunk stack was removed this round; test_server_tools.py gates re-introduction.

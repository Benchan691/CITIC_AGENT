name: false-positive-analysis
description: Analyze Splunk detection triggers to determine whether activity is malicious, suspicious, benign, or inconclusive, identify repeatable sources of detection noise, and recommend evidence-based tuning without modifying the detection. Use when a detection fires unexpectedly, produces excessive alerts, appears too broad, or may be matching legitimate activity.
---

# Purpose

Determine why a detection triggered and whether the observed activity represents:

- true malicious activity;
- suspicious activity requiring investigation;
- a likely false positive;
- expected benign behavior;
- or insufficient evidence.

The workflow is:

trigger
→ understand detection logic
→ reconstruct triggering event
→ gather surrounding telemetry
→ test competing explanations
→ identify repeatable benign pattern
→ assess false-positive confidence
→ propose safe tuning
→ hand off detection change

This skill analyzes and recommends.

It does not modify Splunk detections.

# When to use

Use this skill when:

- a Splunk detection appears to have fired on legitimate activity;
- analysts repeatedly close similar alerts as benign;
- a rule produces unexpectedly high alert volume;
- a detection condition appears too broad;
- a user, host, process, IP, application, service account, or workflow repeatedly triggers a rule;
- an analyst wants to know why a detection fired;
- tuning or suppression may be required;
- an existing exclusion may be too broad or too narrow;
- a proposed detection should be checked for obvious benign patterns before tuning.

Do not use this skill for general threat investigation without a detection trigger.

Use `splunk-investigation`.

Do not create or modify the detection in this workflow.

Use `detection-engineering` after the tuning recommendation has been justified.

# Core Principle

A false positive is not:

"an alert that looks harmless."

A useful false-positive conclusion requires evidence that the detection matched activity which satisfies its technical conditions but does not represent the intended malicious or suspicious behavior.

Do not classify activity as benign merely because:

- the username is familiar;
- the source IP is internal;
- the process is signed;
- the application is approved;
- the host is a server;
- the activity happened before;
- the alert happened many times;
- no other alert fired;
- the event was generated by an administrator.

All of these may be investigation clues, but none independently proves benign intent.

# Available Splunk Tools

Use read-oriented tools for analysis.

## Detection inspection

Use:

`splunk_get_detection`

to retrieve the current rule definition without executing it.

Review:

- SPL;
- description;
- search window;
- schedule;
- enabled state;
- actions;
- detection scope.

## Query safety

Use:

`splunk_validate_query`

before executing new SPL.

## Investigation searches

Use:

`splunk_search`

for bounded supporting searches.

## Scope for supporting searches

Determine scope from evidence in this order where applicable: existing detection SPL;
known company or environment conventions; user-provided incident context; email
evidence; previous Splunk search results; then pivots from returned events.

Never guess an index or sourcetype. If scope is uncertain, state that clearly
and use a carefully bounded exploratory search only when justified.

- `splunk_list_saved_searches(name="term", app="optional-app")`
  - discover an alert by partial name before using `splunk_get_detection` with its exact name.

## Existing saved searches

Use:

`splunk_run_saved_search`

when an existing saved search is relevant and running it is more appropriate than recreating the SPL.

## Detection backtesting

A proposed tuning candidate may be evaluated through read-only backtesting when appropriate.

Use:

`splunk_validate_detection`

and:

`splunk_backtest_detection`

only to evaluate the proposed logic.

Do not create, update, enable, or disable the detection from this skill.

# Evidence Categories

Evaluate several evidence categories before reaching a conclusion.

## Trigger Evidence

Understand exactly what caused the rule to match.

Examples:

- process name;
- command line;
- source IP;
- destination IP;
- user;
- hostname;
- authentication outcome;
- file hash;
- domain;
- event ID;
- threshold;
- event count;
- sequence;
- time condition.

## Context Evidence

Look at surrounding activity.

Examples:

- events immediately before the trigger;
- events immediately after;
- process parent and child relationships;
- associated authentication;
- network connections;
- related DNS queries;
- file activity;
- privilege changes;
- account behavior.

## Historical Evidence

Determine whether the same behavior happened previously.

Examples:

- same user performing the same action;
- same process on the same host;
- same service account across servers;
- same destination used regularly;
- recurring maintenance window;
- repeated automated task.

## Peer Evidence

Compare against similar entities where useful.

Examples:

- other users with the same role;
- hosts in the same server group;
- other domain controllers;
- other application servers;
- other service accounts;
- other endpoints running the same software.

## Environmental Evidence

Consider known infrastructure and operational behavior.

Examples:

- vulnerability scanners;
- backup tools;
- deployment systems;
- monitoring platforms;
- administrative scripts;
- security products;
- scheduled jobs;
- software distribution;
- load balancers;
- proxies.

Environmental familiarity does not automatically make activity benign.

# False-Positive Categories

When a benign pattern is supported, classify the underlying cause.

Useful categories include:

## Expected Administrative Activity

Example:

An administrator legitimately executes a command commonly associated with attacker behavior.

## Service Account Activity

Example:

An automation account repeatedly performs an operation that the detection interprets as suspicious.

## Security Tool Activity

Example:

A vulnerability scanner or EDR component performs behavior similar to attack reconnaissance.

## Software Deployment

Example:

A deployment system executes PowerShell or remote management operations across many hosts.

## Scheduled Automation

Example:

A legitimate scheduled job produces behavior that triggers a threshold rule.

## Application Behavior

Example:

A business application generates network or authentication patterns resembling malicious behavior.

## Shared Infrastructure

Example:

A proxy, NAT gateway, mail relay, or load balancer makes many unrelated events appear to originate from one entity.

## Detection Logic Too Broad

Example:

The SPL matches a generic command or event without requiring the contextual conditions that make the behavior suspicious.

## Threshold Too Sensitive

Example:

Normal activity routinely exceeds the configured event-count threshold.

## Missing Context

Example:

The rule cannot distinguish legitimate and malicious behavior because required fields are unavailable.

## Data Quality Problem

Example:

Field extraction, timestamp parsing, duplication, or ingestion behavior causes incorrect matches.

# Workflow

## 1. Identify the Trigger

Establish the alert or detection being analyzed.

Record when available:

- detection name;
- alert identifier;
- trigger time;
- user;
- host;
- source;
- destination;
- relevant event IDs;
- significant fields;
- original alert evidence.

Do not begin tuning until the actual triggering condition is understood.

# 2. Retrieve the Detection

Use:

`splunk_get_detection`

Review the exact current SPL.

Identify:

- base search;
- indexes;
- sourcetypes;
- filters;
- transformations;
- aggregation;
- thresholds;
- grouping fields;
- time window;
- suppression logic;
- exclusions.

Do not analyze an assumed version of the rule when the real definition is available.

# 3. Explain Why It Triggered

Translate the relevant SPL into detection logic.

Identify the minimum conditions required for a match.

For example:

Detection logic:

- Windows process creation event;
- process is PowerShell;
- command line contains encoded command;
- user is not SYSTEM.

Then map the triggering event against those conditions.

Example:

Condition: PowerShell process  
Observed: `powershell.exe`  
Result: matched

Condition: encoded argument  
Observed: `-EncodedCommand`  
Result: matched

Condition: user != SYSTEM  
Observed: `DOMAIN\alice`  
Result: matched

This establishes why Splunk produced the alert.

It does not yet establish whether the activity was malicious.

# 4. Define Competing Hypotheses

Do not investigate only the benign explanation.

At minimum consider:

## Malicious hypothesis

The activity represents the intended threat behavior.

## Benign hypothesis

The activity is legitimate and happens to satisfy the detection conditions.

## Alternative hypothesis

The alert may result from:

- incomplete telemetry;
- incorrect field extraction;
- duplicate events;
- NAT/proxy effects;
- reused accounts;
- automation;
- incorrect detection assumptions.

Investigate evidence that can differentiate these explanations.

# 5. Inspect Surrounding Activity

Use bounded Splunk searches around the trigger.

Start with a narrow time window.

Useful pivots include:

- same user;
- same host;
- same process;
- parent process;
- child process;
- source IP;
- destination;
- related authentication;
- related DNS;
- related network activity;
- same session;
- same process ID when available.

Ask:

"What happened immediately around this alert?"

Context often determines whether behavior is suspicious.

# 6. Inspect Process Context When Relevant

For process-based detections examine:

- executable;
- path;
- command line;
- parent process;
- child processes;
- user;
- host;
- integrity level if available;
- process hash;
- signer if available;
- network activity;
- file activity.

A legitimate executable can still perform malicious activity.

Do not whitelist based only on process name.

Prefer contextual combinations.

Weak:

`process_name=powershell.exe`

Better:

specific trusted parent
+ known script path
+ service account
+ expected host group

# 7. Inspect Identity Context When Relevant

For authentication or account detections examine:

- user;
- source IP;
- destination;
- authentication method;
- result;
- failure reason;
- device;
- previous authentication;
- subsequent activity;
- privilege level;
- historical behavior.

Do not whitelist an entire user simply because the user is legitimate.

Accounts can be compromised.

# 8. Inspect Network Context When Relevant

For network-based detections examine:

- source;
- destination;
- destination port;
- protocol;
- DNS;
- proxy behavior;
- NAT;
- connection frequency;
- historical communication;
- other hosts contacting the same destination.

Do not whitelist an IP or domain only because it has been seen before.

# 9. Check Historical Frequency

Search previous occurrences of the same relevant pattern.

Questions include:

- How often has this happened?
- When did it begin?
- Is it periodic?
- Does it align with business hours?
- Does it align with maintenance windows?
- Is it associated with one entity or many?
- Did the behavior suddenly change?

A repeating pattern may support a benign explanation but repetition alone is not sufficient.

Malicious persistence can also repeat.

# 10. Establish a Baseline

Where useful, compare the trigger against normal activity.

Possible dimensions:

- user;
- host;
- process;
- source;
- destination;
- hour;
- day;
- command;
- parent process;
- application.

Useful questions:

- Is this normal for this user?
- Is this normal for this host?
- Is this normal for this application?
- Is this normal for peers?
- Is the volume normal?
- Is the timing normal?

Avoid claiming statistical significance from a very small sample.

# 11. Compare Similar Alerts

When repeated alert noise is suspected, examine multiple instances.

Look for stable common attributes.

For example:

Alert 1:
- user = svc_backup
- parent = backup-agent.exe
- host = DB01

Alert 2:
- user = svc_backup
- parent = backup-agent.exe
- host = DB02

Alert 3:
- user = svc_backup
- parent = backup-agent.exe
- host = DB03

A repeatable combination may represent a tuning candidate.

Do not generalize from one event when broader evidence is available.

# 12. Identify the Benign Mechanism

A good false-positive explanation should describe the mechanism.

Weak explanation:

"Probably legitimate admin activity."

Strong explanation:

"The command was launched by the approved deployment agent under the deployment service account on application servers during the scheduled deployment window. The same parent-child process chain occurred on 18 application servers during three previous deployments."

The goal is to understand why legitimate behavior satisfies the detection.

# 13. Determine Classification

Use one of the following classifications.

## True Positive

Evidence supports the detection's intended suspicious or malicious behavior.

## Likely True Positive

Evidence strongly supports suspicious activity but important confirmation is missing.

## Inconclusive

Available evidence does not reliably distinguish malicious from benign activity.

## Likely False Positive

Evidence strongly supports a benign mechanism, but some uncertainty remains.

## Confirmed False Positive

The triggering behavior is supported by sufficient evidence as expected legitimate activity and the reason for the match is understood.

Use `Confirmed False Positive` conservatively.

# 14. Assign Confidence

Use:

- `High`
- `Medium`
- `Low`

## High

Multiple independent evidence points support the conclusion and important conflicting evidence has been investigated.

## Medium

The explanation is well supported but some important context is missing.

## Low

The conclusion depends heavily on assumptions or incomplete telemetry.

Do not artificially increase confidence because the analyst expects a false positive.

# 15. Identify Tuning Dimensions

If the event is likely or confirmed benign, identify which attributes distinguish it from suspicious activity.

Possible dimensions include:

- specific service account;
- host group;
- asset role;
- process path;
- parent process;
- signed binary;
- script path;
- command pattern;
- destination;
- source;
- application;
- event subtype;
- authentication method;
- maintenance window.

Prefer combinations that describe the legitimate behavior precisely.

# 16. Avoid Dangerous Exclusions

Avoid broad exclusions such as:

`user=administrator`

`src_ip=internal_network`

`process=powershell.exe`

`host=domain_controller`

`domain=trusted-domain.com`

These can hide real attacks.

Prefer narrow contextual conditions.

Example:

Rather than:

`NOT user=svc_deploy`

prefer evidence-supported logic resembling:

`NOT (user=svc_deploy AND parent_process=approved_agent AND host_group=application_servers)`

when those conditions genuinely define the benign workflow.

The exact SPL must match the available fields and environment.

# 17. Test the Tuning Hypothesis

Before recommending a tuning condition, determine whether it would suppress only the intended benign pattern.

Ask:

- How many historical alerts would this exclusion remove?
- Would known suspicious examples also match it?
- Is the condition based on stable attributes?
- Could an attacker easily inherit or imitate the trusted attribute?
- Does the exclusion depend on a single weak field?
- Does the tuning create a blind spot?

Prefer narrowing malicious criteria over blanket allowlisting when possible.

# 18. Evaluate Candidate Rule

When appropriate, construct a candidate detection definition without writing it.

Use:

`splunk_validate_detection`

to validate it.

Then use:

`splunk_backtest_detection`

with a bounded historical window.

Compare:

## Existing Logic

- match count;
- known noisy events;
- suspicious examples.

## Candidate Logic

- match count;
- benign events removed;
- suspicious events retained;
- unexpected new gaps.

Do not describe reduced alert volume alone as successful tuning.

The goal is:

reduce known benign noise while preserving meaningful detection coverage.

# 19. Check for Overfitting

Before recommending tuning, ask whether the rule is being tuned to one specific incident.

Warning signs include:

- excluding one hostname unnecessarily;
- excluding one user when the real pattern is an application workflow;
- excluding one IP that may change;
- matching an exact command when many legitimate variants exist;
- suppressing a single alert rather than fixing the detection logic.

Prefer tuning around the underlying benign mechanism.

# 20. Consider Detection Redesign

Sometimes exclusion is not the best solution.

Recommend redesign when:

- the base condition is inherently common;
- legitimate and malicious behavior cannot be separated with current fields;
- too many exclusions are required;
- the detection depends on unstable strings;
- threshold logic is fundamentally wrong;
- better contextual data exists.

Possible redesigns include:

- requiring additional context;
- using behavioral correlation;
- changing aggregation;
- changing threshold;
- adding entity context;
- changing time window;
- using a more appropriate field;
- moving from raw indicators to behavior.

# 21. Preserve Important Suspicious Evidence

Do not suppress an entire pattern if some examples remain suspicious.

For mixed results:

benign subset
→ candidate tuning

suspicious subset
→ preserve detection coverage

unknown subset
→ continue investigation

False-positive tuning must not discard unresolved suspicious activity.

# 22. Recommend the Change

When tuning is justified, document:

- current detection behavior;
- false-positive mechanism;
- supporting evidence;
- proposed condition;
- expected effect;
- possible blind spots;
- validation result;
- backtest result;
- confidence.

Do not apply the change.

Hand the proposed tuning to:

`detection-engineering`

# Safety Rules

- Do not modify detections.
- Do not enable detections.
- Do not disable detections.
- Do not silently suppress alerts.
- Do not create allowlists without explicit detection-engineering review.
- Do not assume internal activity is benign.
- Do not assume signed binaries are benign.
- Do not assume administrator activity is benign.
- Do not assume service-account activity is benign.
- Do not classify an alert from one weak indicator.
- Do not fabricate environmental context.
- Do not fabricate historical baselines.
- Do not fabricate user roles or asset roles.
- Do not claim a false-positive rate without sufficient labelled data.
- Do not hide suspicious evidence to justify tuning.
- Validate new SPL before executing it.
- Keep investigation searches bounded.
- Separate observations from hypotheses.
- Preserve uncertainty when evidence is incomplete.

# Evidence vs Inference

Always distinguish these.

## Observed Evidence

Directly present in Splunk or the supplied evidence.

Example:

`svc_backup` executed `powershell.exe` on `DB01` at 02:00.

## Supported Inference

Reasonable conclusion derived from observed evidence.

Example:

The activity is consistent with the backup workflow because the same process chain occurs during previous scheduled backup windows.

## Unsupported Assumption

A statement not established by available evidence.

Example:

`svc_backup` is definitely safe because it is a service account.

Do not use unsupported assumptions as tuning justification.

# Tuning Quality Criteria

A good tuning recommendation should be:

## Evidence-Based

Supported by observed events.

## Specific

Targets the actual benign mechanism.

## Stable

Uses attributes unlikely to change unnecessarily.

## Narrow

Avoids excluding unrelated activity.

## Testable

Can be validated against historical events.

## Reversible

Can be reviewed and changed later.

## Coverage-Preserving

Retains visibility into suspicious variants.

- Likely False Positive

## Confidence

Use:

- High
- Medium
- Low

Explain the basis.

## False-Positive Mechanism

## Proposed Tuning

Provide:

- tuning objective;
- candidate condition;
- evidence supporting it;
- expected alerts removed;
- suspicious coverage that must remain.

## Tuning Risk

Describe possible blind spots or ways an attacker could match the exclusion.

## Validation and Backtest

When performed, include:

- validation result;
- historical window;
- current rule match count;
- candidate rule match count;
- known benign matches removed;
- suspicious matches retained;
- limitations.

## Limitations

Document missing or uncertain information such as:

- incomplete logs;
- missing asset context;
- missing identity context;
- short historical period;
- unavailable endpoint telemetry;
- ambiguous fields;
- insufficient labelled examples.

## Recommended Next Action

Choose the most appropriate next step:

- continue investigation;
- obtain missing telemetry;
- collect more examples;
- keep detection unchanged;
- hand tuning proposal to `detection-engineering`;
- escalate suspicious activity for analyst review.
